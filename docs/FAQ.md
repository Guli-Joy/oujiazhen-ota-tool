## 查询与数据

### 为什么很多旧版本在官方列表里看不到

因为官方接口只肯给**每个分支的当前最新包**，历史版本需要程序自己“倒着走”才能挖出来，而这条链有它的极限：

1. **分支扫描（广度）**：把 `A` 到 `Z` 26 个分支各问一遍，每个分支只能拿到**当前最新**的那一个包。这一步保证「每个分支都有数据」，但**一个分支只给一个版本**。
2. **升级链回溯（深度）**：拿到最新包的 `realOtaVersion` 后，把它**原样回送**给服务器，服务器会返回它上一级的版本，如此逐级往回走（最多 **40 步**）。这一步才把**中间历史版本**补出来。之所以要单独做，是因为有些中间版本在分支扫描里根本不会出现。
3. **更早的版本（超出 40 步，或服务器已下线该链）**：官方接口已经不再返回，此时**只能靠社区源 VioletToolBox** 补历史清单。

所以看到的现象是：同一个机型里，**官方来源**通常只有几十个（每分支一个 + 链上几十个），**社区来源**反而补出更多老版本。若社区源当天不可用（网络、服务维护），程序会自动降级为「仅官方」，状态栏会少掉「社区源补 N 个」的提示——这是**预期行为**，不是 bug。

### 输入机型名查不到结果怎么办

按可能性排序：

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 左侧列表一个机型都不匹配 | 关键词写法和内置表不一致 | 换成**代号**再试（如 `RMX3888`），或只输入名称里最有辨识度的一段（如 `GT5`） |
| 匹配到机型，但查询后为空 | **海外版代号**、**已停更/已下线的老机型**、**平板/手表等非手机品类**，官方通常没有数据 | 状态栏会提示「海外机型代号或已下线机型通常没有数据」，这属于正常结果 |
| 一直转圈不出结果 | 网络到官方服务器不通（公司网/校园网/代理） | 关掉代理或换网络；直连 `component-ota-cn.allawntech.com` 需能访问 |
| 提示服务器错误码 | 机型代号拼错（如把 `0` 打成 `O`） | 核对代号；`2004` 表示该分支确实没有包，`2100` 表示参数不被接受 |

内置表之外的新机型可以**直接输代号**查询（右侧「按代号查」），不受 539 款名单限制。

### 卡片上的链接已失效标记是什么意思

社区源的历史版本链接是**第三方转发地址**，存放时间久了可能被上游清理。程序会在后台批量探测这些链接，探测失败就在卡片上标「链接已失效」。

- 官方来源的包通常不会这样标记（直链是每次查询时新签发的）。
- 标了「链接已失效」的卡片仍可看到版本信息（版本号、Android 版本、大小），只是下载按钮不可用。
- 这不影响你换一个**更新的版本**下载。

## 直链与下载

### 直链为什么只有 10 分钟

因为那不是「固定网址」，而是 **CDN 的签名地址**。真实下载地址形如：

```
https://…/downloadCheck?…            ← 官方给的入口（无签名，不能直接下大文件）
        │  302 重定向（带 Range: bytes=0- 与 userId 头）
        ▼
https://…/xxx.zip?Expires=1762…&Signature=…   ← CDN 签名直链，约 10 分钟有效
```

签名里带着**过期时间戳**（`Expires=` 或 `x-oss-expires=`）和**摘要**。过期后 CDN 会直接拒绝，这是 CDN 厂商的防盗链机制，**不是本工具的限制**，也无法绕过。

对本工具而言这完全不影响使用：

- 点「下载」时，每个分块请求都会用**当时有效**的直链；
- 单个分块失败重试时（第 2 次尝试起），程序会**自动重新申请直链**再继续，所以下 3 小时的大包也不需要你手动换链；
- 只有你**手动复制直链**给外部工具（IDM / aria2）时，才需要在 10 分钟内开始下载；超时了回来重新点一次「直链」即可。

### 下载中断了怎么办

**什么都不用做，直接点「继续下载」。**

- 进度是分块粒度记录的（8 MB 一块），存在 `<文件名>.partstate` 里，程序被关掉、断电、蓝屏之后依然有效。
- 续传时**已完成的块会被跳过**，只下缺的块，**不会重复占用磁盘**（文件在开始时就已预分配为最终大小）。
- 支持跨天续传：今天下到 40%，明天打开程序重新查一次这个机型、点同一个版本，会接着下。

几种中断情形的差别：

| 情形 | 结果 |
| --- | --- |
| 点「暂停」 | 100 ms 内落一次位图，进度不丢 |
| 直接关窗口 / 杀进程 | 最多丢失最后 5 秒内完成的块，其余进度都在 |
| 断网 / 网络抖动 | 单块自动重试最多 **12 次**（指数退避），期间界面显示重试中；彻底失败会报错并保留进度 |
| 磁盘满 | 报「无法预分配磁盘空间（需要 x GB）」，清理后重试 |

> 注意：**换了保存目录**等于换了一个新任务，旧目录里的 `.partstate` 不会被自动搬过去；想续传就还放回原目录。

### 线程数该设多少

默认 **16**，可在底栏 1–64 之间调。

- **不一定要拉满**：瓶颈通常在服务器侧带宽与你的线路，线程过多反而加重拥堵、触发限速，速度可能不升反降。
- **建议**：家宽 200 Mbps 以上、服务器响应正常 → 16–24 足够；网络较差或服务器响应慢 → 8 左右；连接经常超时 → 先降到 4 试试。
- 线程数与**文件正确性无关**：块编号与线程编号没有绑定关系，任意线程数落盘结果逐字节相同（见 [README · 下载与校验](../README.md#下载与校验)）。

### MD5 对不上怎么办

程序会在下载完成后自动做一次全文件 MD5 校验，不一致会明确报错而不是当作成功：

> MD5 校验不符（得到 …），文件可能损坏，建议删除后重新下载

处理顺序：

1. **先重下一次**。多数情况是某次网络传输/写入被打断造成的偶发问题，重下通常就好了。
2. **检查磁盘**。剩余空间不足、坏道、或杀软实时扫描中途锁文件，都会导致写坏。换个目录（比如别的盘）再试一次。
3. **确认不是「同名不同包」**。社区源与官方源可能有**同版本号但不同哈希**的包（不同地区/不同编译）。以卡片上该来源给的 MD5 为准。
4. **仍不一致**：说明服务器端提供的哈希或文件本身有问题，请把「机型代号 + 版本号 + 卡片上的 MD5 + 报错文本」一起反馈。

补充说明：**多线程分块 + 断点续传不会破坏 MD5**——每个字节都写在自己固定的偏移上，续传只是跳过已完成的块，最终文件与单线程下载逐字节相同。完整论证见 [README · 下载与校验](../README.md#下载与校验)。

### partstate 文件是什么以及能不能删

它**就是**断点续传的进度记录，与目标文件同目录、同名，后缀 `.partstate`。内容只有两行：

```
8589934592                   ← 总字节数
1111100000111110000…         ← 分块位图，'1' 完成 / '0' 未完成，每字符 = 8 MB
```

- **能删**，但删了就等于**放弃续传**，下次从头下。
- 程序在下载**成功或失败后都会自动删除**它，正常结束时不该残留。
- 若总大小或块数对不上（比如你换了下同名文件），程序会**自动作废**它并重下，不会把文件写坏。

## 历史下载与续传

### 关掉程序后还能接着下吗

**能。** 下载进度存在目标文件旁边的 `.partstate` 里，程序退出不会删它（只有下载成功或失败才删）。

重新打开程序 → 点顶栏右上角「**历史下载**」→ 找到那条记录 → 点「**继续下载**」。已完成的分块会被直接跳过，只下缺的部分。

> 续传只认「位图 + 总大小 + 块数」三者都对得上。总大小或块数变了（例如同名文件换了包），位图会被**自动作废**并从头下——这是防止把两个不同版本的文件拼在一起。

### 历史下载里的记录会不会丢

不会丢在下载目录里。历史文件是：

```
%APPDATA%\OujiazhenOtaTool\history.json
```

它在用户配置目录，不会往你的下载目录里丢任何额外文件。删掉它只是清空列表，磁盘上已下好的 `.zip` 不受影响。

另外，历史里的**状态是按磁盘实况推出来的**，不是只信记录：

- 文件在、大小对 → 「已完成」
- 只有 `.partstate` → 「已暂停」，可续传
- 文件被外部删了 → 「失败」，提示重新下载

所以即使你在资源管理器里手动删了文件，历史也能正确反映出来（点「重新扫描」可强制重算）。

### 为什么历史里有的记录显示「不可续传」

因为它对应的 `.partstate` 已经不在了（被删、被杀软清掉、或者下载早已成功完成）。没有位图就没有断点信息，只能从头下，此时按钮显示「重试」而不是「继续下载」。

## 售后包

### 售后包与普通全量包的区别

| | 普通官方全量包 | 售后（降级 / 维修）包 |
| --- | --- | --- |
| 主要用途 | 系统**升级**、同版本重装、救砖 | 系统**降级**、售后维修刷机 |
| 数据来源 | OTA 服务器 `component-ota-cn.allawntech.com` | 官方降级服务器 `downgrade.coloros.com`，或社区源收录的降级包 |
| 直链有效期 | 约 **10 分钟**，过期自动重签 | **长期有效，不换签** |
| 加密方式 | AES-256-CTR + RSA-OAEP(SHA1) | AES-256-GCM + RSA-OAEP(SHA1) |
| 断点续传 | 支持（8 MB 分块） | 支持（直链长期有效，续传更省心） |
| 风险 | 相对低 | **会清空数据**，且跨大版本降级可能失败 |

要点：

- 售后包是给**降级**和**维修**场景准备的，不是「更高级的全量包」。日常升级请用普通全量包。
- **降级一定清空数据**，动手前先备份。
- 是否能降、能降到哪个版本，取决于具体机型的防回滚策略；本工具只负责把包**找出来**，不保证一定能刷进去。
- 来源角标显示「**售后**」（官方降级服务器）或「**社区售后**」（社区源收录），与官方 / 社区并列；售后分区排在列表**最前面**，因为这类包通常只有 1–2 个（升级包往往二十几个，放后面等于藏起来）。

### 社区售后包与官方售后包有什么区别

社区售后包来自 VioletToolBox 社区源：它的版本清单里有一类条目的名字带「**降级包**」后缀（实测全库 41 条），程序把这些条目单独识别出来，并入同一个“售后全量包”分区。

| | 官方售后包 | 社区售后包 |
| --- | --- | --- |
| 角标 | 售后 | 社区售后 |
| 签发方 | ColorOS 官方降级服务器 | VioletToolBox（作者 Smart-Paocai）转发的第三方站点 |
| 直链有效期 | **长期有效，不换签** | 约 **10 分钟**，过期需重新换取 |
| MD5 | 服务器下发 | 无，只有文件大小 |
| 覆盖范围 | 只下发该机型**当前允许降级**的那一两个包 | 社区自行收录，可能包含更老、官方已不提供的降级包 |

要点：

- 同一个分区里**官方在前、社区在后**：官方直链长期有效且带 MD5，先给更好的那个。
- 两者**不会互相去重**。官方卡的版本号读自包内 `version_name`，社区写的是它自己的版本名，字符串对不上；硬比会把同一个包列两遍，反而让人以为「少了一个版本」。宁可多一张卡。
- 社区降级包的大小、日期、补丁级别是程序换取直链后读 ZIP 首部补出来的（见下一问）。社区给的 `security_patch` 有些是 `2088-08-05` 这类占位值，程序按年份合理性判断直接丢弃。
- 社区源是免费公共服务，程序对它只做**三路并发**的补齐请求，不做全量轰炸。

### 为什么有的机型没有售后包

分三种情况，程序会分别告诉你：

| 界面表现 | 含义 | 你要做什么 |
| --- | --- | --- |
| 有「售后全量包 N 个」卡片 | 查到了 | 直接用 |
| 「该机型的官方数据里没有售后全量包」 | 官方确实没给这台机器准备降级包 | 无解，等官方放包 |
| 「售后全量包这次没查到」+ 橙色提示条 | 服务器这轮抽风了，不代表没有 | 点右上角「重新扫描」多试一次 |

**为什么会有第三种**：OPPO 的降级服务器大约有 40% 的请求会返回 500（`AES decrypt error`），程序会自动重试 8 次；仍失败时，宁可诚实地说「这次没查到」，也不谎报「没有」。

**为什么以前「只有某个机型有」**：项目号（决定能查哪些包）藏在官方 OTA 响应里，早期版本只在 `A/F/C/B/E/D` 六个分支里找，而老机型和平板的项目号常常在 H / J / L / M 等分支下 —— 于是它们被误判成「官方没给」。现在改为扫 A–Z 全部分支，实测 143 款原本「查不到」的机型全部都能查到；其中 66 款真的有售后包，其余确实为空。

**那剩下的机型呢**：官方确实不下发降级包的机型，会自动看社区源里有没有收录它的降级包（角标「社区售后」）。这一路**不需要项目号**，所以能覆盖到官方通道根本进不去的那批机型。

### 为什么售后卡显示的不是 ColorOS16.1.0

因为**降级服务器本身就不下发真实版本号**。同机型所有售后包，服务器给的 `colorosVersion` 都是 `ColorOS16.1.0` 这种只剩大版本的字符串，靠它根本分不清是哪个包。

所以程序在查询后，对每个售后包**额外发一次 64 KB 的 Range 请求**，从 ZIP 首部读出 `META-INF/com/android/metadata`（未压缩、明文 key=value），解析出真正的 `version_name`（如 `RMX3888_16.0.10.500(CN01)`）、`ota_version`、`android_version`、安全补丁级别与构建时间，再回填到卡片上。

- 成本约 **64 KB / 包**，并发执行，不拖慢查询；
- 单个包读失败只影响它自己（回落到服务器给的粗版本号），不影响整次查询；
- 这就是为什么你能在售后卡上直接看到真实版本号，而不必下完 10 GB 才知道下的是什么。

### 为什么有的售后卡发布日期是「未知」

社区源只给版本名，**不给文件大小、发布时间和安全补丁级别**。程序对每个社区售后包先换取一次直链，再发一次 64 KB 的 `Range` 请求读 ZIP 首部的 `META-INF/com/android/metadata`：

- 文件大小来自响应的 `content-range`（形如 `bytes 0-65535/8336370448`，斜杠后面就是总大小）；
- 发布日期取自 `post-timestamp`（真正的构建时间，而不是服务器「此刻」的时间）；
- 安全补丁级别取自 `security_patch` 或 `post-security-patch-level`。

只要有一条读不到（个别 CDN 会拒绝 Range，或包首部结构不同），这几栏就保持「未知」，**但不影响下载**——补齐只是显示层的事。

> 顺带一提：realme 有一部分包把补丁日期写成 `2088-08-05` 这种明显虚构的值，程序会按年份做 2010–2030 的合理性判断，超出范围的直接丢弃，宁可不显示也不显示假日期。

### 为什么售后包文件名带售后两个字

因为**售后包与官方包可能有完全相同的版本号**。实测 RMX3888 两者都叫 `RMX3888_16.0.10.500(CN01)`，但官方包 8.76 GB、售后包 10.24 GB。

如果落盘文件名一样，两个任务就会撞上**同一个 `.partstate` 位图**——位图的总大小校验会发现不一致并作废，导致续传失效（严重时来回重下）。所以售后包统一加后缀：

```
RMX3888_16.0.10.500(CN01).zip        ← 官方包
RMX3888_16.0.10.500(CN01)_售后.zip   ← 售后包
```

社区售后包同理：**社区清单里的版本号也可能与某个普通版本撞上**（实测 `RMX3706_14.0.0.903(CN01)` 就有两个不同文件），一样加 `_售后` 后缀。

## 安全与权限

### 杀毒软件报毒怎么办

先说明它**为什么**可能被误报：

- 程序是**未签名的单文件 exe**（无代码签名证书），Windows SmartScreen 会对所有这类文件提示「未知发布者」——这是**发布者信誉**提示，不是查毒结论。
- 程序会**发起 HTTPS 请求、写文件、调用 Windows Shell（`SHOpenFolderAndSelectItems` / `ShellExecuteExW`），必要时请求一次 UAC helper 打开资源管理器**，这些行为在启发式引擎眼里与某些下载器同形。
- 因为用了 `panic = "abort"` + LTO + `strip`，二进制被压得很小且符号被剥离，某些引擎会因此给出低置信度告警。

处理建议：

1. 确认你拿到的 exe 来自**你自己构建**或可信来源；
2. 把文件加入杀软**信任列表/排除项**（Windows Defender：设置 → 病毒和威胁防护 → 管理设置 → 排除项）；
3. **不要**为了运行它而关闭实时防护。
4. 仍不放心就**自己构建**：源码全在仓库里，`cargo build --release` 一条命令即可，见 [README · 构建说明](../README.md#构建说明)。

### 需要管理员权限吗

**不需要。**

- 程序只在用户目录（默认「下载」文件夹，或你自选的目录）里读写文件；
- 配置/缓存写在 `%TEMP%\ota-tool\`，无需系统目录权限；
- 全程只走普通 HTTPS，不装驱动、不写注册表、不改系统设置。

只有当你想把文件存到**受保护目录**（如 `C:\Program Files`）时，才需要相应权限——换个目录即可，不必提权。

### 程序会把我的信息上传吗

不会。

- 只向三个服务器发起**只读查询**：官方 OTA 服务器、社区源 `violettool.top`、售后降级服务器 `downgrade.coloros.com`。
- 不收集设备信息、不上报使用数据、不含任何统计 SDK。
- 随请求发出的只有协议要求的形式参数：官方通道是**随机生成的 `deviceId`**（每次会话随机，与你的真实设备无关）；售后通道需要协议规定的 **DUID 与项目号**（DUID 是公开的协议标识串，不含任何个人信息），且这个请求里不带任何账号凭据。
- 售后包查询后的 ZIP 首部读取（`Range: bytes=0-65535`）是**直接向 CDN 拉 64 KB**，不经过任何第三方。
- 本地只写三类文件：`%TEMP%\ota-tool\violet-catalog.json`（社区源机型目录，公开数据，1 天过期）、`%APPDATA%\OujiazhenOtaTool\history.json`（下载历史）、以及你自己指定保存目录里的 `.zip` / `.partstate`。

## 其他

### 支持 Mac / Linux 吗

**当前只支持 Windows 10 / 11 x64。**

- 界面基于 eframe/egui（跨平台框架），但下载路径、资源管理器定位（`SHOpenFolderAndSelectItems` / `ShellExecuteExW` / 按需 UAC helper，Win10/Win11）、默认目录（`%TEMP%`）等实现是 Windows 专属的；
- 项目的网络与下载层是**同步阻塞 + 原生线程**（ureq + `std::thread`），没有引入 tokio 之类的异步运行时，理论上移植成本不高，但**目前没有官方支持的 Mac / Linux 构建**。

### 为什么程序体积这么小

`Cargo.toml` 里对 release 做了体积优化：`opt-level = "z"`、`lto = true`、`codegen-units = 1`、`panic = "abort"`、`strip = true`。

同时 `.cargo/config.toml` 设置了 `-C target-feature=+crt-static`，**静态链接 C 运行库**——好处是**单个 exe 即可运行，目标机器不需要装 VC++ 运行库**；代价是体积略增（相对于动态链接）。
